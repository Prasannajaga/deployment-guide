# Qwen3.8-27B vLLM DSpark disaggregated recipe

Experimental NVIDIA Dynamo recipe for the supplied Qwen3.8-27B target and
RadixArk Qwen3.8-27B-DSpark draft model:

- target: [`Qwen/Qwen3.8-27B`](https://huggingface.co/Qwen/Qwen3.8-27B)
- draft: [`RadixArk/Qwen3.8-27B-DSpark`](https://huggingface.co/RadixArk/Qwen3.8-27B-DSpark)

The topology is one logical model replica split into one prefill worker and one
decode worker. Both workers use TP=1 and request one H100 GPU. The frontend is
also one replica and requests no GPU.

```text
Frontend:       1 replica, no GPU
Prefill:        1 replica x TP=1 = 1 GPU
Decode:         1 replica x TP=1 = 1 GPU
Total:          2 GPUs, one P/D replica pair
Frontend entry: python3 -m dynamo.frontend
Worker entry:   python3 -m dynamo.vllm
Routing:        round-robin (one P/D pair; no KV-event plane required)
KV transfer:    NIXL over the existing qwen-roce RDMA network
Speculation:    vLLM DSpark, 5 speculative tokens initially
```

This is deliberately a correctness-first recipe. `--enforce-eager` is enabled
because DSpark plus NIXL P/D is sensitive to CUDA-graph and attention-backend
combinations. Remove that flag only after the first smoke test is correct and
the installed image has been validated with this exact target/draft pair.

## Compatibility gate

The repository's older examples use `nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.3.0`
(vLLM 0.23.0). This recipe uses the current stable Dynamo runtime image
`nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.4.0` because Qwen3.8 and the Qwen3
DSpark implementation require a newer vLLM path. Do not silently substitute the
older image.

The frontend intentionally uses the matching vLLM runtime image, as in the
official Dynamo vLLM DGD templates, but it does **not** launch a vLLM engine.
Its container command is explicitly `python3 -m dynamo.frontend --http-port
8000 --router-mode round-robin`. Only the prefill and decode containers launch
`python3 -m dynamo.vllm` and request GPUs.

The first preflight checks that the image contains the Qwen3 DSpark model
implementation. It does not prove that the particular Hugging Face draft
checkpoint is compatible; the model-cache Job and the first request provide
those checks. If the capability check or first request fails, keep the recipe in
experimental status and inspect the image/model combination before scaling it.

The same `--speculative-config` is intentionally passed to both P and D. vLLM
DSpark adds speculative-decoding KV structures; configuring only the decode
worker can make the NIXL producer/consumer KV-layer counts disagree.

### Required Qwen3 drafter metadata fix

The supplied RadixArk draft checkpoint declares `DSparkDraftModel` in its
`config.json`. vLLM uses that architecture name for the DeepSeek-V4 DSpark
class, which expects DeepSeek-only fields such as `hc_mult`. For this Qwen3
drafter, the architecture marker must be `Qwen3DSparkModel`. The download Job
below applies this idempotent metadata-only fix after downloading the draft;
the model weights are not modified.

## 2. Check cluster prerequisites

This recipe assumes the existing shared `model-cache` PVC, the
`qwen32-bench/qwen-roce` secondary network, and one available `rdma/ib` device
on each of two GPU-capable nodes. Only two GPUs are requested, but the P and D
workers should be placed on different nodes when the goal is to measure NIXL
network transfer rather than same-node transport.

```bash
kubectl get crd dynamographdeployments.nvidia.com
kubectl get pvc -n "$NAMESPACE" model-cache
kubectl get network-attachment-definition qwen-roce -n "$NAMESPACE"
kubectl get nodes \
  -o custom-columns='NODE:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu,RDMA:.status.allocatable.rdma/ib'
kubectl get pods -n "$NAMESPACE" -l "$GRAPH_LABEL"
```

Do not continue unless `model-cache` is `Bound`, the secondary network exists,
and the selected nodes advertise the requested GPU and RDMA resources.

## 4. Create the model-cache Job

The quoted `EOF` keeps `$MODEL_NAME`, `$DRAFT_MODEL_NAME`, and the other
container-side variables intact. This Job downloads both the target and draft
repositories into the existing shared PVC.

```bash
mkdir -p "$MODEL_CACHE_DIR"
tee "$MODEL_CACHE_DIR/model-download.yaml" >/dev/null <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: qwen38-27b-dspark-download
spec:
  backoffLimit: 2
  activeDeadlineSeconds: 43200
  template:
    metadata:
      labels:
        app: qwen38-27b-dspark-download
    spec:
      restartPolicy: Never
      containers:
        - name: model-download
          image: python:3.12-slim
          command:
            - /bin/sh
            - -c
          args:
            - |
              set -eu
              pip install --no-cache-dir huggingface_hub==1.16.4
              hf download "$MODEL_NAME" --revision "$MODEL_REVISION"
              hf download "$DRAFT_MODEL_NAME" --revision "$DRAFT_MODEL_REVISION"

              TARGET_CACHE="$HF_HOME/hub/models--Qwen--Qwen3.8-27B"
              DRAFT_CACHE="$HF_HOME/hub/models--RadixArk--Qwen3.8-27B-DSpark"
              TARGET_CONFIG="$(hf download "$MODEL_NAME" config.json --revision "$MODEL_REVISION")"
              DRAFT_CONFIG="$(hf download "$DRAFT_MODEL_NAME" config.json --revision "$DRAFT_MODEL_REVISION")"
              test -s "$TARGET_CONFIG"
              test -s "$DRAFT_CONFIG"

              # RadixArk's Qwen3 drafter is shipped with the generic
              # DSparkDraftModel marker. vLLM maps that marker to the
              # DeepSeek-V4 DSpark class, so select the Qwen3 DSpark class.
              python3 - "$DRAFT_CONFIG" <<'PY'
              import json
              import os
              import sys

              path = sys.argv[1]
              with open(path, encoding="utf-8") as handle:
                  config = json.load(handle)

              architectures = config.get("architectures", [])
              if "DSparkDraftModel" in architectures:
                  config["architectures"] = ["Qwen3DSparkModel"]
                  temporary = path + ".tmp"
                  with open(temporary, "w", encoding="utf-8") as handle:
                      json.dump(config, handle, indent=2)
                      handle.write("\n")
                  os.replace(temporary, path)

              if config.get("architectures") != ["Qwen3DSparkModel"]:
                  raise SystemExit(
                      f"unexpected Qwen3 DSpark architectures: {config.get('architectures')}"
                  )
              print(f"Qwen3 DSpark architecture verified: {path}")
              PY

              du -sh "$TARGET_CACHE" "$DRAFT_CACHE"
          env:
            - name: MODEL_NAME
              value: Qwen/Qwen3.8-27B
            - name: DRAFT_MODEL_NAME
              value: RadixArk/Qwen3.8-27B-DSpark
            - name: MODEL_REVISION
              value: main
            - name: DRAFT_MODEL_REVISION
              value: main
            - name: HF_HOME
              value: /model-store
            - name: HF_HUB_DOWNLOAD_TIMEOUT
              value: "120"
            - name: HF_XET_HIGH_PERFORMANCE
              value: "1"
          envFrom:
            - secretRef:
                name: hf-token-secret
                optional: true
          resources:
            requests:
              cpu: "4"
              memory: 16Gi
            limits:
              cpu: "8"
              memory: 32Gi
          volumeMounts:
            - name: model-cache
              mountPath: /model-store
      volumes:
        - name: model-cache
          persistentVolumeClaim:
            claimName: model-cache
EOF

kubectl delete job "$DOWNLOAD_JOB" -n "$NAMESPACE" --ignore-not-found
kubectl apply --dry-run=server -n "$NAMESPACE" \
  -f "$MODEL_CACHE_DIR/model-download.yaml"
kubectl apply -n "$NAMESPACE" -f "$MODEL_CACHE_DIR/model-download.yaml"
kubectl wait -n "$NAMESPACE" \
  --for=condition=Complete \
  "job/$DOWNLOAD_JOB" \
  --timeout=43200s
kubectl logs -n "$NAMESPACE" "job/$DOWNLOAD_JOB" --tail=100
```

If either repository is private or gated, create `hf-token-secret` before
running the Job. Keep the token in the Secret; never put it in this README or
in a manifest literal.

- `VllmPrefillWorker.replicas: 1`, TP=1, one GPU, NIXL `kv_producer`.

- `Frontend.replicas: 1`, no GPU.
- The target and DSpark draft are loaded by both worker processes. This costs
  more memory than a normal prefill-only worker, but keeps the P/D KV layout

## 8. Tune speculative decoding after correctness

The starting configuration is:

```json
{
  "method": "dspark",
  "model": "RadixArk/Qwen3.8-27B-DSpark",
  "num_speculative_tokens": 5,
  "draft_tensor_parallel_size": 1
}
```

`num_speculative_tokens` is the number of draft tokens proposed per target
verification step. Test `3`, `5`, and `7` with the same prompts and compare
accepted tokens per target pass, output-token throughput, TTFT, TPOT, and GPU
memory. Keep the value identical on prefill and decode, regenerate the manifest,
and delete/recreate the graph between trials so old compilation artifacts do not
affect the result.

The target and draft must share a compatible tokenizer/vocabulary for strict
verification. If the draft model's config declares a different maximum block or
prediction count, use the value supported by that draft rather than forcing a
larger number.

After the eager baseline is correct, test CUDA graphs as a separate experiment.
Do not remove `--enforce-eager` and change the speculative-token count in the
same trial. A useful first comparison on recent vLLM builds is:

```text
--compilation-config '{"cudagraph_mode":"FULL"}'
```

If that comparison produces hangs, garbled output, or first-request crashes,
return to `--enforce-eager`; the issue is runtime/image compatibility, not a
reason to change the P/D replica count.

## 9. Troubleshooting

### Model download fails

Inspect the Job before changing the deployment:

```bash
kubectl logs -n "$NAMESPACE" "job/$DOWNLOAD_JOB" --tail=200
kubectl describe job -n "$NAMESPACE" "$DOWNLOAD_JOB"
```

An unknown repository, gated repository, missing token, or insufficient PVC
capacity must be fixed in the cache step. Do not let the workers download from
the network independently.

### `Qwen3 DSpark implementation is missing`

The runtime image is too old or is not the expected vLLM build. The repository's
vLLM 0.23.0 image is not the default for this recipe. Use the stable 1.4.0 image
shown above or a tested newer image, update all three image fields in the
quoted manifest block, regenerate `deploy.yaml`, and rerun the capability check.

### `AttributeError: 'Qwen3Config' object has no attribute 'hc_mult'`

This is the draft metadata routing failure shown in the supplied log. vLLM has
selected `vllm.models.deepseek_v4.nvidia.dspark.DSparkDeepseekV4ForCausalLM`
instead of the Qwen3 DSpark implementation. Do not add `hc_mult` to the Qwen3
config. Re-run the model-cache Job from this README so its JSON patch changes
the draft architecture to `Qwen3DSparkModel`, then verify the Job log contains
`Qwen3 DSpark architecture verified` before restarting the DGD.

The `Enforce eager set` and `Cudagraph is disabled under eager mode` lines are
expected with this recipe. The `max_num_scheduled_tokens` warning is addressed
by the 8192 `--max-num-batched-tokens` setting; it is not the engine-startup
failure.

### `Number of KV layers must match between producer and consumer`

Confirm that both workers have the same DSpark JSON, `--kv-cache-dtype`,
`--max-model-len`, and block size. This recipe intentionally enables the same
speculative config on P and D. Delete the graph, regenerate the manifest, and
reapply it after correcting any mismatch.

### GPU out of memory

This is a one-GPU-per-worker recipe, so do not raise TP to hide the issue. First
reduce `--max-model-len` to `16384` and `--max-num-seqs` to `1` on both workers.
If weights plus the draft still do not fit, the supplied checkpoint format is
not viable on one H100 for this topology; use a compatible quantized target or
request a different topology.

### NIXL or UCX connection failure

Check the secondary interface and RDMA resources on both worker Pods:

```bash
kubectl describe pod -n "$NAMESPACE" \
  -l "$GRAPH_LABEL"
kubectl logs -n "$NAMESPACE" -l "$GRAPH_LABEL" \
  --all-containers --prefix | grep -E 'NIXL|UCX|RDMA|mlx5|NixlConnector'
```

Verify that `mlx5_8:1` is the HCA exposed to the Pod's `qwen-roce` attachment.
If the node uses a different HCA, change `UCX_NET_DEVICES` in both workers and
rerun the deployment. Keep the same UCX settings across P and D.

### Request hangs or produces incorrect output

Keep `--enforce-eager`, use `temperature: 0`, and test one request at a time.
If the eager baseline is correct but a CUDA-graph trial is not, revert the graph
trial. If the eager baseline fails, capture both worker logs and test the target
without `--speculative-config` only as a diagnostic; that changes the experiment
and is not the requested recipe.

## 10. Cleanup

Stop the port-forward with `Ctrl-C`, then remove only this graph and its
completed download Job. The shared PVC and both model snapshots are preserved.

```bash
kubectl delete dynamographdeployment.nvidia.com "$DEPLOYMENT" \
  -n "$NAMESPACE" --ignore-not-found
kubectl wait -n "$NAMESPACE" \
  --for=delete pod \
  -l "$GRAPH_LABEL" \
  --timeout=600s
kubectl delete job "$DOWNLOAD_JOB" \
  -n "$NAMESPACE" --ignore-not-found
```
